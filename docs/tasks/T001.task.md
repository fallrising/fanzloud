# Outcome

The Technical Design and accepted ADR define an implementable, testable, private personal-BYOS
boundary for operating the project owner's Codex subscription on their own cloud host.

# Inputs

- TD §0.4, §1.2, §1.4, §1.6, §2.2, §2.3, §5.1, §6, §8–§10
- Official Codex authentication, headless-login, non-interactive execution, and app-server
  documentation
- ADR-0002

# Deliverables

- Accepted ADR-0002.
- Updated P0 authentication boundary and acceptance outcome.
- Trusted credential-runner and provider-managed execution boundaries plus updated INV-002 and
  INV-007.
- Complete P0 Contract Unit inventory.
- T001–T007 dependency graph with machine acceptance.
- Traceability entries for the P0 decision and tasks.

# Non-scope

- Production Rust or web implementation.
- Multi-user, public, or subscription-resale operation.
- Claude Code, Cursor Agent, or Grok adapters.
- Private Git credentials, arbitrary repositories, submodules, hooks, or push.
- Local repository execution, interactive Codex approvals, and app-server integration.

# Invariants

- Subscription credentials are never shared or returned to the browser.
- Only the operator's own officially authenticated account is used.
- Credential state never enters a repository execution environment or downloadable artifact.
- Every production task remains specification-first.

# Dependency Evidence

T000 implementation commit `76f72b364c179983e0b99b84c19b7f9822a0968a` passes all local gates. T000
remains conditional pending hosted CI, so T001 remains Blocked until T000 is Accepted.

# Decomposition

T001 is the documentation and contract boundary. T002–T006 each own independently testable public
boundaries, and T007 is the explicit cross-module integration and release-acceptance task.

# Risks and Gaps

- T000 hosted CI is not yet available, so T001 cannot become Ready.
- Codex CLI must be pinned to an exact released version during T002/T003 specification.

- Provider terms and technical support must be rechecked before broadening beyond personal BYOS.
