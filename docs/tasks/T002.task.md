# Outcome

Provide a trusted, single-operator login broker that runs the pinned official Codex CLI in an
operator-owned `CODEX_HOME` and exposes only login status or bounded provider verification
instructions to the private control plane.

# Inputs

- TD §§1.6–1.7, 2.2, 2.3, 8.2–8.10, 11.3 P14, and 15.0
- ADR-0002 §§Credential boundary and First execution interface
- T001 P0 boundary
- T010 domain value and error foundation
- Current Codex manual: Configuration, Authentication, and Models; Authentication and sessions;
  Login on headless devices

# Deliverables

- A version-pinned Codex executable configuration owned by trusted operator infrastructure.
- A per-operator `CODEX_HOME` lease and permission check outside repositories and disposable
  workspaces.
- Device-login start, status, and bounded completion/failure lifecycle behind typed errors.
- Redacted login instructions and status projections that cannot contain auth tokens, `auth.json`,
  or arbitrary process output.
- Fake-CLI lifecycle, concurrency, permission, crash/reconciliation, and secret-canary tests.

# Non-scope

- API-key or browser-supplied access-token login.
- Repository checkout, prompts, `codex exec`, `codex app-server`, Codex Cloud task submission, or
  repository-controlled process execution.
- Multi-user tenancy, credential sharing, token export, or persistent browser sessions.

# Invariants

- The broker runs only the administrator-configured Codex executable with fixed login arguments.
- `CODEX_HOME` is outside repositories and permission-restricted to the operator runner.
- Credentials never enter prompts, argv, general environment, logs, events, artifacts, responses, or
  downloads.
- At most one login operation owns an operator scope at a time.
- An interrupted login is reconciled through `codex login status` before any retry.
- The browser receives status or provider verification instructions, never credential material.

# Dependency Evidence

T001 and T010 are implemented and their local/hosted checks pass, but both remain `verifying`
because fresh acceptance reports are unavailable. T002 therefore remains Blocked.

# Risks and Gaps

The exact provider device-code output shape and process exit semantics are not a stable contract in
the current public Codex manual. `SPEC-T002` records a `[TD-GAP]`; implementation is blocked until
the contract is resolved by a captured pinned-CLI fixture or an ADR/specification decision.
