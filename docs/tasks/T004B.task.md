# Outcome

Project an accepted Cloud submit into one recoverable provider-task lifecycle, including normalized
status, explicit operator reconciliation, browser-disconnect independence, and cancellation
semantics.

# Inputs

- TD §§2.3 INV-005, INV-006, INV-012, 4.8, 5.1, 8.2–8.10, 11, 14, and 15.0
- ADR-0002
- Accepted T004A

# Deliverables

- One explicit provider-task lifecycle state machine and typed redacted public operations.
- Candidate adoption for an unknown submit without automatic retry.
- Ordering, termination, cancellation, backpressure, crash, and recovery tests.
- Exact local turn-cancellation semantics that do not claim provider-side cancellation.

# Non-scope

Executing or applying a diff, local repository tools, HTTP transport, browser rendering,
multi-session persistence, and the generic `AgentBackend` trait.

# Invariants

- Browser disconnect does not alter provider task state.
- No submit operation produces more than one automatic Cloud exec.
- An unknown submit remains blocked until an explicit, validated reconciliation outcome.
- Cancellation never claims the provider task stopped unless the pinned provider surface proves it.

# Dependency Evidence

T004A is Accepted by [`ACCEPT-T004A`](../acceptance/T004A.acceptance.md). T004B is the sole Ready
production task.

# Specification

Normative contract: [`SPEC-T004B`](../specs/SPEC-T004B-cloud-task-lifecycle.md).

# Machine Acceptance

Run every named SPEC-T004B lifecycle, stream, recovery, cancellation, and fault test plus the
workspace gates.

# Risks and Gaps

The pinned CLI has no Cloud cancel command. SPEC-T004B therefore defines explicit cancellation as a
local Codebox lifecycle transition, retains the provider task reference for later inspection, and
requires the UI to disclose that the provider task may continue.
